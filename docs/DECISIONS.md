# 决策记录

按时间顺序。每条记「决定了什么 / 为什么 / 有没有替代方案被否掉」。

---

## D1 · 自建 vs 直接用现成的

**决定**：在开源基线之上做自己的版本（最终选择 fork 上游 Lidless）。

**背景**：调研发现这个品类已被做透。与本项目规格几乎重合的两个上游：

- `nghialuong/Lidless`（MIT）——SMAppService + XPC + 看门狗 + 热/电闸 + 定时，覆盖面约等于本项目 P0+P1
- `Vigil`（nav-ai.net）——合盖保持唤醒 + AI agent 会话 + root helper + 电量下限 + 过热保护

**理由**：规格里的差异项（三档粒度、档位锁定、中文、接自家链路）上游没有，且我们本来就打算做菜单栏 App 而非纯脚本。

**代价**：要承担 fork 的长期维护，每个 macOS 大版本可能都要跟。

## D2 · 项目名：NightCat

**决定**：NightCat。

**背景**：候选名里曾重点考虑 **Hearth**（炉火不灭，隐喻与"三档=火候"天然对应），但最终由用户定为 NightCat（夜猫）。

**命名避雷清单**（睡眠工具领域已被占用，勿再使用）：

> Amphetamine、Caffeine、Theine、Lungo、InsomniaX / InsomniaT / InsomniaZ、KeepingYouAwake、Capsomnia、Clapet、NeverNap、Owly、NoSleep、NoDoze、Caffeinated、Espresso、PleaseSleep、SmartSleep、One Switch、**Lidless**、**Vigil**

其中 Lidless 被至少两个开源项目占用且功能就是本项目要做的；Vigil 有多个同名 Mac app，其中一个功能完全重合。

> ⚠️ NightCat 这个名字**尚未做商标 / App Store 查重**。若要对外分发，先查。

## D3 · 三档而非两档

**决定**：屏幕常亮 / 防空闲 / 合盖不睡，递进关系。

**理由**：三档对应三种真实场景（演示看盘 / 后台跑批 / 无人值守）。上游只有合盖 on/off，合盖档对普通场景太重（强制不锁屏风险 + 耗电）。

## D4 · 提权用 SMAppService + LaunchDaemon helper

**决定**：正规方案，而非 sudoers 免密。

**理由**：一次授权长期可用；不改动系统 `/etc/sudoers.d`；上游已实现且经过验证。

**否掉的替代**：sudoers 免密（10 分钟能做出来，但等于给 `pmset` 开后门，且 `0ssamaak0/Lidless` 的做法就是这样）。

## D5 · 电池下不让程序替用户做主

**决定**：提示后由用户决定，不静默降级；<20% 直接拒绝；拔电源同样走提示流程。

**理由**：静默降级会让"我明明开了却没生效"变成难排查的问题；拔电源瞬间静默切换可能正好中断一个长任务。

## D6 · 图标用「颜色 + 倒计时」，砍掉状态点

**决定**：图标本体着色表档位；倒计时仅在设了定时器时出现；合盖档强制显示倒计时。

**否掉的方案**：状态圆点——与颜色是同一信息通道，冗余。

## D7 · 单击开面板，不直接切档

**决定**：单击图标打开面板，档位在面板里切。

**理由**：三档 + 定时 + 电池闸的信息量放不进"点一下就切"的交互。

## D8 · 定时到点直接关，不逐级回落

**决定**：直接关闭全部档位。

**理由**：逐级回落（合盖→防空闲→屏幕→关）行为不可预测，且用户很难预期"现在到底是哪一档"。

## D9 · 加档位锁定

**决定**：锁定当前档位，切换需二次确认；不跨重启保留。

**理由**：批处理跑着时误点切换会中断任务。

**否掉的替代**：不做锁定，只靠"操作要慎重"的自觉——不符合这个 App 的定位。

## D10 · 砍掉 CLI

**决定**：不做 CLI。这是本规格里最容易被重新提出的一条，**不要加回来**。

**分析过程**：CLI 的受众是脚本 / AI agent / 远程会话，不是人工（人工点菜单栏更快）。但系统自带的 `caffeinate -i <cmd>` 已经覆盖约 90% 的场景（包住命令、命令结束即释放）。摊开算，`NightCat` 的 CLI 相对 `caffeinate` **只多一件事**：把「合盖不睡」绑到命令生命周期上。

**结论**：唯一增量能力是"合盖档 + 命令生命周期"，当前工作流用不上。等真出现"无人值守 + 合盖 + 需要脚本控制"的需求再回来讨论。

**连带收益**：CLI 砍掉后，原本的架构冲突（helper 的 90 秒看门狗会在 CLI 驱动时误杀）自动消失，**helper 保持上游"薄"的现状即可**，不需要把状态机搬进去。

## D11 · 砍掉 URL Scheme

**决定**：不做。

**理由**：价值在 Shortcuts / Raycast / Alfred 触发，等价于"键盘唤出代替鼠标点菜单栏"。当前无此流程。

## D12 · 拆除 Sparkle 自动更新

**决定**：拆。

**理由（安全性质）**：`project.yml` 里 `SUFeedURL` 指向 `raw.githubusercontent.com/nghialuong/Lidless/main/docs/appcast.xml`，`SUPublicEDKey` 是上游的公钥。不拆的话，本 fork 会去**上游服务器**检查并拉取更新。

**替代**：日后若需要分发，再搭自己的 appcast（需自建 EdDSA 密钥）。当前不需要。
